Scoped presentation

Search-as-Code: let the model generate the retrieval program.

The core idea is not “agentic search” broadly. It is a sharper architecture: expose search primitives as an SDK, let the model write code, execute that code in a sandbox, and compare it against fixed pipelines and tool-calling agents.

Perplexity SaC: model + sandbox + Agentic Search SDK Our eval: 6,010-doc enterprise benchmark Primary metric: Recall@10
What we should say first.

Search-as-Code moves control below the monolithic search API: retrieval, ranking, filtering, fanout, and aggregation become programmable.

What our eval shows.

On the full real-LLM custom test, agentic codegen reaches 0.7081 Recall@10; agentic preset reaches 0.5809; one-shot codegen reaches 0.5779.

What the matrix changes.

We now compare fixed flow, preset stacks, one-shot codegen, and agentic variants with the same Recall@10 plus total/codegen/execution latency.

Why it matters

Traditional search is too rigid for agents

  • A monolithic search endpoint controls the downstream pipeline.
  • Agents need task-specific fanout, filtering, joining, ranking, and aggregation.
  • Repeated tool calls add latency and pollute model context with intermediate results.

Perplexity Research, Jun 1 2026

What changed

Code becomes the search orchestrator

  • The model generates Python search pipelines.
  • The sandbox executes deterministic compute: batching, retries, filtering, joining, dedupe.
  • The Agentic Search SDK exposes search primitives rather than only final resultsets.

Perplexity reports SaC outperforms other agent systems on 4 of 5 benchmarks and ties closely on HLE.

Architecture

Search-as-Code has three layers.

This is the framing we should use in the presentation.

1. Model as control plane

Reason about the task, decompose evidence needs, decide retrieval strategy, and generate code.

2. Sandbox as runtime

Run generated code safely; handle deterministic control flow, batching, filtering, serialization, retries, and aggregation.

3. Search SDK as I/O layer

Expose low-level search primitives: retrieval, ranking, filtering, fanout, document rendering, intermediate candidate state.

Our evaluation

We built a benchmark around enterprise search control.

The test is designed for Search-as-Code: fanout, joins, exact identifiers, metadata filters, negative evidence, rerank budget control, and reflection.

6,010documents
48tasks, 31 test
5,942hard distractors
266hard-negative labels

How the dataset is built

  1. Start with source-of-truth docs. 68 core or near-core documents: account briefs, escalations, security advisories, tickets, releases, runbooks, alias registries, approval ledgers, and authority matrices.
  2. Add realistic noise. 5,942 structured hard distractors in same-topic clusters: stale drafts, duplicate tickets, wrong versions, ambiguous aliases, dashboards, Slack-style notes, and near-duplicate approvals.
  3. Label the task. Each query has a gold answer, evidence doc IDs, hard-negative IDs, required operations, and expected search routes. Exports include corpus/tasks/hard negatives plus BEIR-style qrels.

Index and test stack

corpus.jsonl -> title + text + metadata -> BM25 token index -> MiniLM dense vectors -> hybrid search API -> CrossEncoder rerank
  • Open-source components: rank_bm25, sentence-transformers all-MiniLM-L6-v2, spaCy query understanding, optional Wikidata linking, and ms-marco-MiniLM CrossEncoder reranking.
  • Exposed controls: mode, top_k, BM25 weight, include/exclude doc types and sources, must/should/exclude terms, and rerank candidate budget.
  • Measured costs: raw mean latency, search calls/query, candidate pool size, and rerank pairs. No normalized latency score.

Example queries in the test set

Alias + approval For CT-R's OAuth review, which Beacon version is customer-citable after final approval, and which version must be rejected?

Reflection policy A generated query found 900 candidates but no approval ledger. Should it stop or generate follow-up code?

Tests whether reflection looks for missing evidence categories, not only candidate count.

What this setup stresses

  • Dynamic route selection: decide when to use hybrid, BM25, dense, rewrite, alias expansion, exact identifiers, and metadata filters.
  • Large candidate opportunity: main rerank flows can retrieve up to 2,400 candidates before final top-10 output.
  • Evidence discipline: recover required evidence while avoiding stale or non-authoritative hard negatives.
  • Reflection: generate follow-up retrieval code when customer, ticket, release, approval, or policy evidence is missing.

Current gaps

The benchmark is useful, but not yet production proof.

After improving LLM planning/reflection, quality is no longer the only question. The remaining gaps are cost, scale, answer-level success, and safe fallback behavior.

Gap Why it matters Next action
Real LLM decision points Full test: agentic preset improves from single-router 0.3689 to 0.5809 Recall@10 with evidence-aware reflection. Tune stop criteria against recall, token cost, and tool-call precision.
Real LLM codegen reliability Full test: real agentic codegen reaches 0.7081 Recall@10, but it costs 159.7s/query. Keep full codegen as a hard-case path; optimize prompt size, cache reuse, timeout policy, and model choice.
Answer-level task success Retrieval metrics do not prove the final answer is correct, concise, and grounded. Add answer generation with citation scoring, field-level accuracy, and missing-evidence penalties.
Reflection policy Evidence-coverage reflection drives the Recall@10 lift, but every extra turn adds LLM latency. Learn when to stop: protect confident evidence, add follow-up only for missing required categories, and cap turns by query class.
Production cost and safety Generated programs are more flexible but can add latency, extra search calls, larger rerank pools, and sandbox failures. Track code tokens, result tokens, final-context tokens, timeout rate, sandbox policy violations, and fallback behavior.

Recommendation

Recommended next step: prove the architecture, not just the benchmark score.

The demo should show generated retrieval code, real LLM routing decisions, and why preset-stack agentic search is the practical path before full codegen.

  1. Productize agentic preset search first.
    It reaches 0.5809 Recall@10 on the full real-LLM test at 35.7s/query, much cheaper than full codegen.
  2. Keep full codegen for hard cases.
    It reaches 0.7081 Recall@10, but 159.7s/query means it should be gated, cached, or used offline.
  3. Score final answers.
    Measure answer accuracy, citation grounding, token cost, latency, and failure rate.
  4. Harden context selection.
    Keep authoritative evidence, drop stale drafts, and track hard-negative leakage.
