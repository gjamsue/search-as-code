Scoped presentation

Search-as-Code: let the model generate the retrieval program.

The core idea is not “agentic search” broadly. It is a sharper architecture: expose search primitives as an SDK, let the model write code, execute that code in a sandbox, and compare it against fixed pipelines and tool-calling agents.

Perplexity SaC: model + sandbox + Agentic Search SDK Our eval: 6,010-doc enterprise benchmark Primary metric: Recall@10
What we should say first.

Search-as-Code moves control below the monolithic search API: retrieval, ranking, filtering, fanout, and aggregation become programmable.

What our eval shows.

One-shot Search-as-Code ties fixed enriched at 0.1857 Recall@10, but iterative agentic Search-as-Code reaches 0.4579 by checking missing evidence and writing follow-up retrieval routes.

What is still missing.

The next bar is production proof: real LLM codegen, tool-calling agent baseline, token accounting, and answer-level context selection to filter hard negatives.

Industry reference

Perplexity reframes search as code generation.

The useful industry anchor is Perplexity’s Search as Code architecture, not broad enterprise search positioning.

Why it matters

Traditional search is too rigid for agents

  • A monolithic search endpoint controls the downstream pipeline.
  • Agents need task-specific fanout, filtering, joining, ranking, and aggregation.
  • Repeated tool calls add latency and pollute model context with intermediate results.

Perplexity Research, Jun 1 2026

What changed

Code becomes the search orchestrator

  • The model generates Python search pipelines.
  • The sandbox executes deterministic compute: batching, retries, filtering, joining, dedupe.
  • The Agentic Search SDK exposes search primitives rather than only final resultsets.

Perplexity reports SaC outperforms other agent systems on 4 of 5 benchmarks and ties closely on HLE.

Architecture

Search-as-Code has three layers.

This is the framing we should use in the presentation.

1. Model as control plane

Reason about the task, decompose evidence needs, decide retrieval strategy, and generate code.

2. Sandbox as runtime

Run generated code safely; handle deterministic control flow, batching, filtering, serialization, retries, and aggregation.

3. Search SDK as I/O layer

Expose low-level search primitives: retrieval, ranking, filtering, fanout, document rendering, intermediate candidate state.

Our evaluation

We built a benchmark around enterprise search control.

The test is designed for Search-as-Code: fanout, joins, exact identifiers, metadata filters, negative evidence, rerank budget control, and reflection.

6,010documents
48tasks, 31 test
5,942hard distractors
266hard-negative labels

Dataset scope

  • Simulated enterprise knowledge base: account briefs, escalation logs, security advisories, Jira-style tickets, release notes, runbooks, alias registries, approval ledgers, and policy docs.
  • Tasks require joining customer, alias, product, CVE, ticket, owner, fixed version, source authority, renewal window, and blocker status.
  • Hard distractors are structured into same-topic clusters: draft advisories, duplicate tickets, stale snapshots, ambiguous aliases, wrong-version approvals, war-room drafts, namespace-proof notes, and policy near-duplicates.

What it tests

  • Dynamic route selection: decide when to use hybrid, BM25, dense, rewrite, alias expansion, or exact identifier routes.
  • Large candidate opportunity: main rerank flows can retrieve around 2,400 candidates before final top-10 output.
  • Evidence discipline: recover missing evidence while avoiding stale or non-authoritative hard negatives.
  • Reflection: generate follow-up retrieval code when required evidence categories are missing, not only when candidate pool is thin.

Current gaps

The benchmark is useful, but not yet production proof.

We now have a better dataset and fixed-flow comparison. The remaining gaps are about model behavior, end-task success, and production cost.

Gap Why it matters Next action
Real LLM codegen Current generated flow is deterministic. It validates the architecture, not the model’s ability to write reliable retrieval code. Generate Python from a tool schema; measure codegen latency, invalid-code rate, repair rate, and retrieval quality.
Tool-calling agent baseline This is the real alternative architecture: same tools, but the model decides over multiple turns instead of writing one retrieval program. Run query understanding, rewrite, search, rerank, and reflection as tools; compare quality, latency, tokens, and tool calls.
Answer-level task success Retrieval metrics do not prove the final answer is correct, concise, and grounded. Add answer generation with citation scoring, field-level accuracy, and missing-evidence penalties.
Reflection policy Naive reflection triggered 0/31 times; evidence-coverage reflection is what created the Recall@10 lift. Generalize the goal planner across more enterprise query types and tune when to stop iterating.
Production cost and safety Generated programs are more flexible but can add latency, extra search calls, larger rerank pools, and sandbox failures. Track code tokens, result tokens, final-context tokens, timeout rate, sandbox policy violations, and fallback behavior.

Recommendation

Recommended next step: prove the architecture, not just the benchmark score.

The demo should show generated retrieval code, different flows per query, and a fair comparison against fixed pipelines and tool-calling agents.

  1. Run real codegen.
    Use proprietary models to generate retrieval programs from the same tool schema.
  2. Add the agent baseline.
    Compare against multi-turn tool calling with the same APIs and the same evaluation set.
  3. Score final answers.
    Measure answer accuracy, citation grounding, token cost, latency, and failure rate.
  4. Harden context selection.
    Keep authoritative evidence, drop stale drafts, and track hard-negative leakage.
